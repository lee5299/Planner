# 플랜두씨 다이어리 — PRD 및 구현 프롬프트

작성일: 2026-09-12
관련 문서: [DESIGN.md](./DESIGN.md)

## 1. 코딩 에이전트에게 전달할 실행 지시

이 문서와 DESIGN.md를 읽고 실제로 사용할 수 있는 한국어 플랜두씨 다이어리 웹앱을 구현하라. 소개용 홈페이지가 아니라 사용자가 자신의 계획을 세우고 실제 활동을 기록하며 다음 계획을 조정하는 앱이다. 기존 저장소의 지침, 코드, 실행 환경을 먼저 확인하고 기존 기술 스택이 있으면 존중하라. 화면 목업에서 멈추지 말고 서버 API와 실제 데이터베이스를 연결하고 저장·조회·수정·삭제·새로고침 이후 복원까지 검증하라.

이 문서에서 ‘확정 요구사항’은 사용자와 합의한 내용이다. ‘구현 기본값’은 미정 세부사항을 구현 가능하도록 정리한 제안이며, 확정 요구사항을 바꾸지 않는 범위에서 조정 가능하다. 합의한 내용을 다시 질문하지 말고 합리적인 기본값으로 진행하라. 실제 데이터베이스 접속 정보처럼 실행에 반드시 필요한 정보만 부족할 때 요청하라. 설정되지 않은 연결이나 테스트 성공을 만들어내지 마라.

완료 보고에는 구현 기능, 실행 방법, DB와 환경변수 설정 방법, 실제 수행한 검증 결과, 남은 제한을 적어라. 구현 과정에서 주요 설계 선택의 이유를 짧게 기록하라. 불필요한 문서를 계속 늘리지 마라.

## 2. 제품 목적과 최우선 원칙 — 확정 요구사항

할 일에 체크만 하고 끝나는 도구가 아니다. 내가 계획을 어느 쪽으로 자주 틀리는지 확인하고 돌아보기의 결론이 다음 계획으로 이어지는 도구다. 남의 예시가 아닌 사용자의 실제 계획과 실제 기록이 중심이다.

- Plan → Do → See → 다음 Plan의 흐름을 완성한다.
- 자기관리와 프로젝트는 독립된 메뉴와 화면으로 **완전히 분리**한다. 통합 대시보드, 섞인 캘린더, 합산 점수를 만들지 않는다.
- 자기관리는 자신을 잘 돌보고 있다는 감각을 주는 따뜻한 기록이다. 점수나 달성률을 보여주지 않고 응원과 칭찬으로 표현한다.
- 프로젝트는 계획 대비 실제, 지연과 이슈를 객관적으로 확인할 수 있어야 한다.
- 매일은 클릭 중심으로 간단히 사용한다. 긴 일기, 소요 시간 입력, 타이머를 필수로 만들지 않는다.
- PC 중심이며 따뜻하고 편안한 파스텔 민트 디자인을 사용한다.
- 이번 범위에서는 로그인·회원가입·잠금 기능을 구현하지 않는다. 접근 제한은 다음 과제의 범위다.
- 링크를 아는 누구나 볼 수 있다. 공개해도 괜찮은 내용만 입력하도록 짧게 안내한다. 현재 버전은 개인별 데이터 격리를 보장하지 않는 공유 공간이다.
- 계획·실행 기록·설정은 서버의 실제 DB에 저장한다. 브라우저 메모리나 localStorage만으로 구현하지 않는다.
- 개발 소요시간 또는 과제의 ‘계획시간’ 제한은 요구사항에 포함하지 않는다. 사용자가 프로젝트에 설정하는 시작일·마감일은 별개로 필요하다.

## 3. 정보 구조와 주요 사용 흐름

### 독립된 두 영역

- 자기관리: 오늘 기록 / 목표 설정(만다라트) / 주간 돌아보기.
- 프로젝트: 캘린더·TODO / 프로젝트 상세(단계·업무) / 주간 업무 정리.
- 공통 메뉴에는 자기관리, 프로젝트, 필요한 설정만 둔다.
- 마지막으로 사용한 영역을 다시 연다. 첫 방문은 자기관리 화면을 기본으로 한다(구현 기본값).
- 마지막 메뉴 같은 기기별 UI 선호만 localStorage 사용을 허용한다. 실제 기록은 DB가 원본이다.

### 자기관리 흐름

핵심목표와 세부목표 설정 → 실천 항목 등록 → 오늘 목록에서 했다/못했다 기록 → 짧은 응원 → 주간 돌아보기 → 다음 실천이나 목표 조정.

### 프로젝트 흐름

프로젝트의 목표·기간·중요도 입력 → 단계와 가중치 설정 → 권장 일정 확인 → 일일 업무 작성 또는 반복 목표 설정 → 상태 기록·돌발 업무 추가 → 하루 마무리 → 내일 계획 확인 → 주간 정리 → 필요하면 일정 재조정.

## 4. 자기관리 기능

### 4.1 목표 설정 — 확정 요구사항

- 중앙 핵심목표 1개, 주변 세부목표 최대 8개를 둔다.
- 세부목표 각각에 외곽 실천 항목 최대 8개를 둔다. 설정 화면은 만다라트 형태다.
- 핵심목표, 세부목표, 실천 항목은 만다라트의 해당 칸을 클릭하고 입력하는 흐름으로 직접 등록·수정한다. 한 칸을 적용한 뒤 다른 칸을 곧바로 이어서 편집할 수 있다.
- 빈칸을 모두 채우지 않아도 사용할 수 있다. 빈칸은 할 일로 생성하거나 실패로 계산하지 않는다.
- 사용자가 제시한 핵심목표: ‘나의 이상을 따르기’.
- 사용자가 제시한 세부목표: 친절하기, 감사(칭찬)하기, 규칙적인 행동, 독서(명상), 자기개발, 운동하기. 나머지 칸과 외곽 항목을 임의로 채우지 않는다.

### 4.2 매일 기록 — 확정 요구사항

- 평소 기록도 세부목표별 3×3 만다라트로 제공하며 실천 항목 칸 자체를 체크 버튼으로 사용한다.
- 오늘 기록의 실천 칸은 미기록 / 했다 두 상태다. 흰색 칸을 누르면 민트색과 체크 문구가 나타나고 다시 누르면 흰색 미기록 상태로 돌아간다.
- 날짜를 선택해 과거 기록을 확인·수정할 수 있다.
- 기록하지 않은 항목을 자동으로 실패 처리하지 않는다. 과거에 저장된 ‘못했다’ 자료는 데이터 호환을 위해 유지하되 새 화면에서는 미기록 상태로 표시한다.
- 체크는 실제 일일 기록으로 저장되고 날짜가 바뀌어도 이전 기록은 유지된다.

### 4.3 내부 계산과 사용자 표현

확정 요구사항:

- 세부목표의 외곽 8개 중 하루에 기본 4개를 달성하면 해당 세부목표의 내부 기준을 충족한다.
- 기준 개수는 세부목표별로 설정할 수 있다.
- 일별 기록을 바탕으로 주간 피드백을 제공한다.
- 자기관리 화면에는 숫자 점수, 퍼센트, 등급, 순위, 평가용 프로그레스 바를 표시하지 않는다. 툴팁이나 보조 설명에도 숨은 점수를 노출하지 않는다.
- 기준을 설정할 때 필요한 ‘4개’ 같은 설정 수치는 표시 가능하다.
- 기록이 적거나 실천이 적으면 응원하고, 꾸준히 실천했으면 칭찬한다. 기록에 없는 성과나 성격을 단정하지 않는다.
- 자기관리 게임화는 허용한다. 실천 기록에 따라 식물·정원 같은 시각 요소가 천천히 자라거나 작은 기념 표시가 쌓이는 방식으로 제공한다.
- 게임화는 다른 사람과의 비교, 순위, 공개 점수, 실패 벌점에 사용하지 않는다. 기록하지 않은 날에 성장 결과를 초기화하거나 사용자를 압박하지 않는다.
- 게임화 결과는 자기관리의 내부 달성 기준을 바탕으로 표현할 수 있지만, 계산 점수·퍼센트·등급을 화면이나 접근성 문구로 노출하지 않는다.

구현 기본값:

- 내부 일별 값 = min(달성 항목 수 / 해당 날짜의 기준 개수, 1).
- 기준 개수는 1~8, 기본 4. 등록한 항목이 4개 미만이어도 기록을 막지 않고 기준을 낮출 수 있게 한다. 기준을 몰래 변경하지 않는다.
- 그날 실제 기록이 있는 세부목표만 평가한다. 전부 미기록이면 평가 대신 기록을 부드럽게 안내한다.
- 주간은 월요일~일요일, 사용자 시간대 기준. 미래 날짜와 미기록 날짜는 0점으로 넣지 않는다.
- 주간 내부 값은 기록된 날짜별 세부목표 평균을 합산한 후 기록된 일수로 정규화한다. 0.75 이상은 칭찬 중심, 그 미만은 응원 중심으로 문구를 선택한다. 숫자는 표시하지 않는다.
- 데이터가 적으면 ‘꾸준히’ 같은 지속성을 단정하지 않는다. 기록이 없는 주는 ‘이번 주 기록이 아직 없어요. 작은 실천부터 남겨볼까요?’처럼 표현한다.
- 문구는 기록 기반 규칙과 템플릿으로 생성한다. 외부 생성형 AI API를 필수 의존성으로 추가하지 않는다.
- 목표/기준 변경은 오늘부터 즉시 적용한다. 오늘 이후에 이미 만들어진 설정에도 같은 내용을 이어 반영하고, 과거 날짜의 이름·항목·기준은 보존한다. 기록이 있는 항목 삭제는 보관 처리한다.

### 4.4 자기관리 돌아보기

주간 화면은 짧은 응원 또는 칭찬과 실제 실천 기록을 보여준다. 일일 ‘내일 바꿀 점’은 선택 입력이며 다음 날 자기관리 화면에서만 보여준다. 목표 설정 화면으로 이동해 다음 실천을 조정할 수 있다. 프로젝트의 이슈와 업무를 섞지 않는다.

## 5. 프로젝트 기능

### 5.1 구조와 입력

- 프로젝트 → 순서가 있는 단계 → 일일 업무의 3단계 구조.
- 프로젝트: 이름, 목표 한 줄, 시작일, 마감일, 중요도 상·중·하, 작업 가능한 요일.
- 단계: 이름, 순서, 가중치 정수 1~10, 권장 시작일·종료일, 사용자가 조정한 일정, 상태.
- 업무: 제목, 시작일, 마감일, 상태, 연결 프로젝트·단계, 선택 메모, 지연 사유, 실제 완료일.
- 캘린더와 프로젝트 화면 상단에서 프로젝트 추가를 바로 시작할 수 있다. 저장한 프로젝트 카드를 선택하면 단계 추가 버튼과 단계별 업무가 나타난다.
- 프로젝트 목록은 ‘진행 중’과 ‘전체 보기’로 전환한다. 프로젝트 완료는 현재 계획을 저장한 채 진행 중 목록에서 제외하는 동작이며, 전체 보기에는 완료 프로젝트를 포함한다. 완료 프로젝트 상세에서는 다시 진행 상태로 돌릴 수 있다.
- 프로젝트 중요도는 프로젝트 간 우선순위다. 단계 가중치는 상대적인 기간 비중과 프로젝트 진척도 계산에 사용한다. 둘을 혼동하지 않는다.
- 일일 업무를 미리 작성하거나 필요한 날 추가할 수 있다.
- 갑자기 생긴 일은 제목만으로 빠르게 저장하고 나중에 프로젝트/단계에 연결할 수 있다. 예정일 기본값은 오늘이다. ‘계획 외 업무’ 표시를 보존한다.
- 계획된 업무를 표시할 캘린더와 TODO 목록은 같은 DB 데이터를 사용한다. 한쪽에서 수정하면 다른 쪽도 갱신된다.
- 캘린더의 업무 라벨은 연결 프로젝트에서 선택한 파스텔 색상을 사용한다. 프로젝트가 없는 업무만 중립 색상을 사용한다.
- 프로젝트 탐색 화면은 상단 검색, 바로 아래 상태 메뉴(전체·진행 중·완료), 프로젝트 카드 목록 순서로 구성한다. 다른 화면에서는 가로 프로젝트 바로가기 메뉴를 제공한다.
- 단순한 할 일에도 쓸 수 있도록 프로젝트에 연결되지 않은 업무를 허용한다.

### 5.2 상태와 하루 마무리

- 업무 상태: 할 일 / 진행 중 / 완료 / 보류 / 취소.
- 진행 중 또는 보류에서 ‘시간이 더 필요함’, ‘이슈로 지연’, ‘기타’와 선택 메모를 입력할 수 있다.
- 완료하면 실제 완료 날짜·시각을 기록한다. 완료 취소도 이력으로 남긴다.
- 오늘 미완료 업무에 ‘내일로 이동 / 날짜 변경 / 취소’를 제공한다. 자동으로 다음 날에 옮기지 않는다.
- 이동해도 업무 ID와 최초 예정일을 유지한다. 변경 전후 날짜와 사유를 기록한다.
- 하루 마무리는 상태 확인, 필요한 일정 조정, 선택적인 ‘내일 바꿀 점’ 한 줄, 내일 업무 미리보기로 구성한다.
- ‘내일 바꿀 점’은 다음 날 프로젝트 화면에서 보여준다. 사용자가 확인하거나 수정할 수 있다.
- 미완료 모아보기는 예정일이 지난 미완료 업무를 찾는 기능이며 자동 이월과 다르다.

### 5.3 반복 목표

확정 요구사항:

- 매주 4회 공부처럼 횟수 기준의 반복 목표와 반복 업무를 지원한다.
- 반복 목표의 예시로 주 4회 이상 수행 시 목표 충족으로 판단할 수 있다. 이 수치와 아래 프로젝트명은 기능 설명용이며 앱에 자동 등록하지 않는다.
- 프로젝트 영역은 목표 대비 횟수를 객관적인 수치로 표시해도 된다. 자기관리 숫자 숨김 규칙과 구분한다.

구현 기본값:

- 고정 요일 반복과 ‘주 N회, 요일 자유’ 반복을 구분한다.
- 고정 요일 반복은 날짜별 실행 항목을 중복 없이 생성한다. 주 N회는 사용자가 날짜를 선택하거나 수행 시 기록한다.
- 주 N회 목표는 기본적으로 완료한 날짜 수를 센다. 같은 날 중복 클릭으로 횟수가 늘지 않는다. 기본 단위는 하루 1회다.
- 각 실행 기록은 반복 정의와 별도로 저장한다. 반복 설정 변경·삭제로 과거 실행 기록이 사라지지 않는다.
- 반복 횟수 목표 충족을 필기/실기 단계 완료로 간주하지 않는다. 유한한 하위 업무가 없는 반복 중심 단계는 수동 진척도와 명시적인 단계 완료를 사용한다.
- 단계별 꾸준히 하는 일은 시작일, 종료일, 반복 요일을 설정한다. 저장 시 해당 기간에서 선택 요일에 맞는 일일 업무를 자동 생성하고 중복 날짜는 만들지 않는다.
- 반복 기간이나 요일을 수정하면 완료 기록과 지난 일정은 유지하고, 미완료 미래 일정만 새 범위에 맞춰 갱신하거나 비활성화한다.

### 5.4 진행률

확정 요구사항:

- 단계와 프로젝트의 진척도를 프로그레스 바로 표시한다.
- 바 길이는 진척도, 색상은 일정 여유·주의·촉박 상태다.
- 마우스를 올리면 진행률 %를 표시한다. 키보드 포커스와 터치에서도 확인할 수 있어야 한다.
- 하위 업무 완료 비율을 기본으로 하되 업무 크기 차이를 보정하기 위한 수동 조정을 허용한다.

구현 기본값:

- 단계 진척도 p = 완료된 비취소 업무 수 / 전체 비취소 업무 수. 진행 중 업무에 임의의 50%를 주지 않는다.
- 업무가 없으면 자동 진척도는 0이며 수동 값을 입력하거나 단계를 완료할 수 있다. 반복만 있는 단계는 앞 절의 규칙을 따른다.
- 수동 진척도는 0~100%, 자동 계산으로 복귀하는 기능을 제공한다. 수동 조정 여부와 이력을 보존한다.
- 프로젝트 진척도 P = Σ(단계 가중치 × 단계 진척도) / Σ(단계 가중치).
- 단계가 없거나 전체 가중치가 0인 경우 계산하지 않고 ‘단계 설정 필요’로 표시한다. 가중치 0은 입력 검증으로 차단한다.
- 100% 수동 입력 시 단계 완료 의사를 확인하고 남아 있는 업무를 몰래 완료 처리하지 않는다. 단계 완료와 하위 업무 상태가 충돌하면 정리를 안내한다.

### 5.5 가중치 기반 일정 및 촉박함 판단

확정 요구사항:

- 작업 가능한 요일을 기준으로 프로젝트 기간의 작업 가능일을 센다.
- 가중치 비율로 단계별 권장 기간을 배분한다.
- 작업 가능일 10일, 가중치 1·1·3·5이면 각 단계 권장 기간은 1·1·3·5일이다.
- 뒤쪽에 높은 가중치의 단계가 남으면 단순 완료 업무 개수가 많아도 일정 압박을 알아볼 수 있어야 한다.
- 일정이 밀려도 기존 계획을 자동 덮어쓰지 않는다. ‘일정 재조정’에서 조정안을 제시하고 사용자가 적용한다.

구현 기본값 — 계산을 순수 함수로 분리하고 테스트할 것:

1. 시작일과 마감일을 포함해 선택 요일에 해당하는 작업일 목록을 만든다. 공휴일은 별도 기능 없이 자동 제외하지 않는다.
2. 총 작업일 D, 가중치 w_i에 대해 이론상 배분일 d_i = D × w_i / Σw를 구한다.
3. 계산과 위험 판단은 소수를 유지한다. 날짜 표시는 연속적인 누적 작업일 경계로 매핑한다. 하루보다 작은 단계는 같은 날짜를 공유할 수 있으며 표시 반올림으로 전체 마감일을 넘기지 않는다.
4. 최초 계획과 현재 적용 계획을 버전으로 보존한다. 초기에는 동일하다.
5. 현재 계획의 단계별 총 배분 작업량을 a_i, 진척도를 p_i라 할 때 잔여 예상 작업량 R = Σ[a_i × (1 − p_i)]다.
6. 현재 날짜부터 마감일까지 남은 작업 가능일 A를 센다. 오늘은 하루 단위 기록이므로 종료 처리 전에는 포함하고, 하루 마무리 후에는 제외한다. 실제 시간 단위 추정은 하지 않는다.
7. R > 0일 때 여유율 = (A − R) / R. 20% 이상은 ‘여유’, 0% 이상 20% 미만은 ‘주의’, 음수는 ‘촉박’으로 표시한다. 모든 작업 완료는 ‘완료’가 우선이다.
8. 마감일이 지났는데 미완료이면 ‘기한 초과’. 날짜 또는 작업 요일이 없으면 ‘판단 불가’로 표시하고 여유로 간주하지 않는다.
9. 단계에도 같은 방식으로 단계 종료일과 잔여 작업량을 비교한다. 프로젝트 상태에는 전체 잔여량뿐 아니라 미완료 단계의 종료일 초과를 반영한다. 단계가 밀린 경우 전체를 ‘여유’로 표시하지 않고 최소 ‘주의’와 지연 사유를 보여준다.
10. 이는 사용자가 입력한 가중치와 진척도를 기반으로 한 추정이다. 실제 작업 시간 예측인 것처럼 표현하지 않는다. 세부 근거는 툴팁/상세에만 둔다.

검증 예시: D=10, w=[1,1,3,5]에서 앞의 두 단계만 완료하면 프로젝트 진척도는 20%, 잔여 예상량은 8일이다. 남은 작업일이 5일이면 ‘촉박’이어야 한다.

### 5.6 일정 재조정

- 현재 진척도와 잔여 가중치 w_i × (1−p_i)를 기준으로 남은 작업일을 재배분한다.
- 조정 전후 단계 일정과 작업 압축 정도를 미리 보여준다. 완료 단계는 변경하지 않는다.
- 사용자가 적용할 때만 새 계획 버전을 저장한다. 최초 계획, 변경 이력, 실제 기록은 유지한다.
- 일일 업무 날짜까지 옮길 경우 영향을 받는 업무 목록을 조정안에 포함한다. 숨겨진 일괄 변경은 금지한다.
- 마감이 지난 경우나 남은 작업일이 없는 경우 ‘기간을 다시 설정해 주세요’를 표시한다. 불가능한 조정안을 성공처럼 제시하지 않는다.
- 재조정은 기존 지연을 지우는 기능이 아니다. 주간 정리에서는 최초 계획 대비 차이를 계속 확인할 수 있다.

## 6. 프로젝트 주간 업무 정리 — 객관적인 See

확정 요구사항:

- 선택한 주의 완료 업무, 진행 중 업무, 지연 업무와 사유, 발생한 이슈, 다음 주 예정 업무를 간결히 정리한다.
- 예정일과 실제 진행 상태를 함께 표시한다.
- 자기관리식 응원, 칭찬, 추상적인 생산성 평가를 섞지 않는다.
- 실제 기록을 기반으로 자동 정리한다. 없는 이슈나 지연 사유를 생성하지 않는다.

구현 기본값:

- 월요일~일요일 단위, 프로젝트 필터와 주 이동을 제공한다.
- 완료 목록은 해당 주의 실제 완료일 기준, 진행 중·지연 목록은 해당 주 종료 시점의 상태 이력 기준이다. 이번 주는 현재 시점까지 집계한다.
- 진행 중인 업무의 해당 주 상태 변경과 메모를 보여줘 완료되지 않은 작업도 활동 내역에 남긴다.
- 지연에는 최초 예정일, 현재 예정일, 실제 완료일(있는 경우), 지연 사유를 필요한 만큼 표시한다. 사유가 없으면 ‘사유 미기록’으로 쓴다.
- 이슈는 작성일, 연결 업무/프로젝트, 짧은 내용, 해결 여부로 정리한다.
- 완료 건수, 계획 외 업무 건수, 이월 건수처럼 판단에 필요한 수치만 보여준다.
- 목록을 클릭하면 원본 업무/이력으로 이동한다.
- 지난주 기록이 이후 날짜 변경으로 다시 쓰이지 않도록 이력 기반으로 조회한다. 과거 기록을 명시적으로 수정한 경우에는 수정 여부를 표시한다.

## 7. 데이터와 서버 요구사항

### 필수 저장 대상

- 자기관리 핵심목표, 세부목표, 실천 항목, 설정/기준 버전, 날짜별 상태 기록.
- 프로젝트, 단계, 업무, 반복 정의, 반복 실행 기록.
- 최초 계획과 적용 계획 버전, 일정 변경 내역, 업무 상태 변경 내역, 수동 진척도 변경.
- 이슈, 실제 완료일, 일별 돌아보기와 내일 바꿀 점.

### 권장 데이터 설계 — 구현 기본값

- self_care_goals / self_care_categories / self_care_actions / self_care_settings_history.
- self_care_daily_logs: action_id + local_date 유일성, status, 당시 기준/항목 버전.
- projects / stages / tasks: 정렬 순서, 연결 관계, 원래 예정일, 현재 예정일, 완료일, 상태, 보관 여부.
- recurrence_rules / recurrence_occurrences: 반복 규칙과 날짜별 실행을 분리하고 중복 생성 방지 키를 둔다.
- plan_versions / plan_stage_allocations: 최초/현재 계획과 단계별 배분량 보존.
- task_events / issues: 날짜·상태·완료 취소·지연 사유 등 변경 이력과 이슈.
- daily_reviews: 날짜 + 영역(self-care/project)별 기록. 두 영역의 내일 바꿀 점을 섞지 않는다.
- 모든 핵심 레코드에 ID, 생성/수정 시각을 둔다. 관계와 날짜·가중치·진척도 유효성은 서버에서도 검증한다.

### 저장과 오류 처리

- 서버 DB를 진실의 원본으로 사용한다. 정적 JSON·목업 API·localStorage 단독 구현은 완료가 아니다.
- 새 저장소라면 서버 API와 관계형 DB를 가진 단순한 구조를 선택한다. 기존 스택을 우선하고 불필요한 서비스는 추가하지 않는다.
- 호스팅 환경의 재시작/재배포 후에도 유지되는 DB를 사용한다. 휘발성 서버 파일에만 SQLite를 두지 않는다.
- DB 인증정보는 서버 환경변수로 관리하고 클라이언트 번들에 노출하지 않는다.
- 클릭 저장 중·성공·실패 상태를 제공한다. 낙관적 업데이트가 실패하면 복구하고 재시도를 안내한다.
- 연속 클릭, 중복 요청, 반복 일정 재생성으로 레코드가 중복되지 않아야 한다.
- 업무 변경과 이력 저장, 일정 재조정 적용은 일관된 트랜잭션으로 처리한다.
- 날짜는 사용자 시간대 기준의 달력 날짜, 이벤트 시각은 UTC 저장을 기본으로 한다. 초기 시간대 기본값은 Asia/Seoul이며 설정 가능하게 한다.
- 기록이 있는 대상은 보관 처리하여 과거 돌아보기가 깨지지 않게 한다.
- 현재 버전의 공유 편집 특성을 숨기지 않는다. 로그인 없는 상태에서 개인별 비공개를 약속하지 않는다.

## 8. 실제 초기 자료의 취급

다음은 사용자가 제공한 실제 계획 소재다. 임의의 완료 기록, 구체적인 실천 내용, 확정되지 않은 날짜와 가중치를 만들어 넣지 않는다. 첫 사용 시 비어 있는 앱에서도 시작할 수 있고, 아래 소재는 사용자가 선택해 불러오는 편집 가능한 초안으로 제공한다. 자동으로 실제 완료 데이터처럼 주입하지 않는다.

### 자기관리

- 핵심목표: 나의 이상을 따르기.
- 세부목표: 친절하기 / 감사(칭찬)하기 / 규칙적인 행동 / 독서(명상) / 자기개발 / 운동하기.
- 각 외곽 실천 항목은 미입력, 일일 기준 기본 4개.

### 프로젝트

아래 사례는 프로젝트·단계·가중치 계산을 설명하기 위한 기획 예시이며 초기 데이터, 불러오기 버튼, 반복 목표로 자동 등록하지 않는다.

1. 자격 취득형 프로젝트: 필기와 실기처럼 여러 단계로 나누고 주간 반복 횟수를 설정할 수 있다.
2. 구축형 프로젝트: 학습, 구축, 장비 설정처럼 순서가 있는 단계와 기간을 설정할 수 있다.
3. 과제형 프로젝트: 여러 단계 중 중요도와 기간 비중이 큰 단계를 가중치로 표현할 수 있다.

미정 일정에는 일정 평가를 하지 않는다. 현재 날짜나 임의의 연도를 실제 계획 날짜로 확정하지 않는다. 테스트 데이터는 별도 테스트 DB/fixture에서만 사용한다.

## 9. 범위 제외

로그인·회원가입·잠금·사용자별 권한, 팀 협업·메시지·소셜 기능, 외부 캘린더 연동, 푸시/이메일 알림, 타이머·시간 추적, 의무적인 AI API 연동, 결제, 랜딩페이지용 홍보 섹션, 자기관리 점수·순위 경쟁은 이번 범위에 추가하지 않는다. 개인 기록을 돕는 비경쟁 게임화는 범위에 포함하며 일정 경고는 앱 안에서 제공한다.

## 10. 구현 순서와 완료 검증

1. 저장소 지침과 환경 확인 → 데이터 모델과 핵심 계산 함수 정의.
2. DB 마이그레이션·서버 API·입력 검증·이력 저장 구현.
3. 독립 메뉴와 공통 디자인 → 자기관리 설정·일일 기록·주간 피드백 구현.
4. 프로젝트·단계·업무·캘린더·반복 목표 구현.
5. 진척도·일정 상태·재조정 미리보기·일일/주간 돌아보기 연결.
6. 실제 실행 환경에서 저장·새로고침·오류 처리와 주요 계산을 검증.

필수 수용 기준:

- [ ] 자기관리와 프로젝트가 독립 화면이며 서로의 기록과 피드백이 섞이지 않는다.
- [ ] 마지막 사용 영역을 다시 열고 빈 상태에서도 실제 데이터를 등록할 수 있다.
- [ ] 만다라트의 일부 칸만 등록해도 일일 목록에서 기록 가능하다.
- [ ] 기준 4개에서 4개 이상 달성하면 내부 기준 충족, 기준 변경도 작동한다.
- [ ] 자기관리 어디에도 점수·퍼센트·평가 바가 노출되지 않는다.
- [ ] 미기록을 실패로 계산하지 않고 기록 없는 주에 허구의 칭찬을 하지 않는다.
- [ ] 자기관리 설정 변경 후 과거 기록의 기준과 내용이 보존된다.
- [ ] 프로젝트의 캘린더와 TODO가 같은 저장 데이터를 표시한다.
- [ ] 상태 변경, 돌발 업무 추가, 미완료 이동·취소와 이력이 정상 작동한다.
- [ ] 반복 목표 주 4회 충족, 같은 날 중복 클릭 방지, 주 경계 집계가 올바르다.
- [ ] 가중치 1·1·3·5와 작업일 10일의 배분이 1·1·3·5일이다.
- [ ] 앞 2단계 완료 시 프로젝트 진척도 20%, 잔여 8일, 가용 5일이면 촉박이다.
- [ ] 업무 없음·단계 없음·작업 요일 없음·마감 초과·완료·소수 배분 경계에서 오류가 없다.
- [ ] 바 길이와 상태 색상의 의미가 다르고 hover/focus/tap으로 %를 확인할 수 있다.
- [ ] 재조정은 미리보기 후 적용되며 원계획·완료 기록·기존 지연 이력이 보존된다.
- [ ] 내일 바꿀 점이 다음 날 해당 영역에 표시된다.
- [ ] 주간 업무 정리가 실제 완료일과 당시 상태를 사용하며 사유를 만들어내지 않는다.
- [ ] 저장 후 강제 새로고침 및 새로운 브라우저 세션에서 DB 자료가 복원된다.
- [ ] 서버 저장 실패 시 성공처럼 보이지 않고 중복 요청도 일관되게 처리된다.
- [ ] 단위 테스트는 가중치·위험 판단·주간 집계·반복 중복 방지에 집중하고 주요 UI 흐름은 실제 브라우저에서 확인한다.

위 검증을 실제로 수행한 뒤에만 구현 완료를 보고하라. DB 연결 등 환경 때문에 수행하지 못한 검증은 별도로 명시하라.
